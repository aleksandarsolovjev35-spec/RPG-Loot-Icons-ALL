# RPG Loot Icons — вырезка иконок из листов

Репозиторий содержит 82 листа (паки 01–41, по 2 части). Скрипт `tools/cut_icons.py`
универсально вырезает иконки:

* **чёрный фон сохраняется** — кроп непрозрачный, берутся все пиксели внутри каймы;
* **серо-белая кайма не попадает в результат** — кроп режется строго по внутренней
  стороне каймы, а случайно оставшиеся внутри пиксели каймы закрашиваются чёрным;
* **листы без каймы режутся по «призрачной сетке»** — паки 39 и 40 (200 иконок),
  где рамок нет, кроются по границам межиконочных зазоров.

Результат: `cut_icons/<пак>/partN/icon_NNN.png` (палитра 255 цветов, ~148×149 для
листов с каймой, ~151×151 для листов без неё). Всего 4100 иконок.

## Универсальный алгоритм

0. **Классификация листа.** `has_frame()` считает, сколько строк/столбцов листа
   состоят из длинных серых прогонов (`sat ≤ 14`, `30 ≤ lum ≤ 240`): у листов с
   каймой таких ≥10 строк и ≥20 столбцов, у листов без каймы — ровно 0. Порог
   проверен на всех 82 листах, разрыв между классами однозначный.
   * есть кайма → шаги 1–5;
   * каймы нет → «призрачная сетка» (шаг 6).

1. **Маска содержимого.** Фон листов почти чёрный; содержимое =
   `luminance > 30` или насыщенный цвет.
2. **Поиск каймы.** Кайма — тонкие (1–4 px) серые линии. Длинные серые прогоны
   (≥30 px) кластеризуются в горизонтальные/вертикальные линии сетки; линия
   считается настоящей, если видна минимум в 3 ячейках листа.
3. **Валидация ячейки.** Прямоугольник ячейки принимается, если у него видно
   ≥3 сторон с покрытием ≥30%, или 2 стороны ≥80%, или одна сторона целиком
   (иконка может перекрывать кайму своим телом).
4. **Карта пикселей каймы.** Для каждого валидного прямоугольника по периметру
   ищутся поперечные сечения линии (1–4 px серого). Сечение считается каймой,
   если снаружи от него фон и либо между линией и иконкой есть зазор, либо
   серая полоса толстая (≥4 px — кайма впритык к иконке + антиалиас).
   Серые блики/контуры самой иконки (1–3 px, сразу подпертые телом иконки)
   каймой не считаются и не трогаются.
5. **Кроп.** Внутренность каймы (±2 px внутрь от линии), остатки каймы внутри
   закрашиваются чёрным. Никакой прозрачности.
5a. **Уточнение сдвинутого тайла (`refine_rect`).** Сетка листа — общая, но
   отдельные тайлы в исходниках сдвинуты вручную (04/part1 — на 15 px,
   14/part2 — на 5, 34/part2 — на 6), а на 13/part2 кайму сверху и снизу
   целиком перекрывает сама иконка. В обоих случаях прямоугольник сетки не
   проходит валидацию по покрытию сторон (0.00–0.67 вместо ≥0.8) и иконка
   молча пропадала: 4 листа из 82 отдавали 49 иконок вместо 50, а нумерация
   остальных съезжала на 1. Теперь такой прямоугольник получает один шанс:
   каждая сторона притягивается к самой сильной серой линии в пределах
   `REFINE_SEARCH = 26 px`, размер сверяется с модальной ячейкой (±12 px), и
   сторона принимается, если линия видна хотя бы на 35 % длины **или** иконка
   нарисована поверх неё (доля контента ≥ 70 % — линия может быть полностью
   спрятана под собственным артом). Проверка на всех 82 листах: 4100 иконок,
   ни одного пересечения рамок, остальные 78 листов отдают байт-в-байт те же
   файлы.
6. **Листы без каймы: «призрачная сетка» (`find_cells_borderless`).** Рамок нет,
   но роль линейки выполняет сама вёрстка листа: между иконками есть полоса
   фона, общая для всего листа. Поэтому сетка восстанавливается по проекциям:

   * **зазоры.** По профилю содержимого (`content.sum(0)` / `content.sum(1)`)
     ищутся максимальные прогоны нулевой суммы длиной ≥4 px — это поля по краям
     и 9 вертикальных + 4 горизонтальных межиконочных зазора. Промежутки между
     соседними зазорами = столбцы и строки сетки. Так как зазор — это фон на
     всю высоту/ширину листа, такая сетка (а) единообразна: все ячейки столбца
     имеют общий x-диапазон, как это делает настоящая рамка, и (б) ничего не
     обрезает: прямо за границей кропа по построению фон.
   * **пропущенная линия.** Единственный способ «съесть» зазор — иконка,
     вылезающая за свою ячейку; тогда зазор исчезает и два столбца склеиваются.
     По центрам найденных зазоров методом наименьших квадратов подводится период
     (здесь 180.5 px), и склеенный интервал деливается на `round(len/pitch)`
     равных ячеек. Валидность сетки: строк и столбцов должно быть ≥2, иначе лист
     помечается как нечитаемый и пропускается (вместо слепого реза).
   * **пустые ячейки** (содержимого < 200 px) отбрасываются, нумерация идётся
     плотным списком в порядке чтения (строки по yT, внутри строки по xL);
   * **кроп на 1 px внутрь с каждой стороны.** Крайняя строка/столбец ячейки —
     это антиалиас самой пластины иконочника (её светимость ≈ 0.4× от соседней:
     частичное покрытие поверх чёрного зазора, замер по всем 200 ячейкам —
     медиана 0.39–0.48). Оставленная краем кадра, эта строка читается как
     лишняя чёрная линия в 1 px, обрывающая градиент пластины, поэтому она
     отрезается. Каймы-то нет, но «шов» на границе тайла есть всегда.
     Сверху/снизу то же самое: градиент пластины там тоже обрывался.

   Из-за этого ячейки без каймы — ~151×151 против ~148×149 у листов с каймой
   (там режем на 2 px внутрь линии рамки).

Размеры иконок не выравниваются — берётся ровно содержимое ячейки.

## Перепаковка в полноцветный WebP (`tools/repack_icons.py`)

`cut_icons.py` сохраняет палитровые PNG на 255 цветов — это теряет градиенты
(медиана уникальных цветов в исходном кропе 9339) и оставляет «плавающий»
размер (21 вариант, 146–153 px, 40 % не квадратные). `repack_icons.py` режет
листы **тем же детектором** (`cut_icons.iter_cell_crops` — нумерация и
геометрия ячеек совпадают с `cut_icons/`) и сохраняет кропы полноцветно:

```
кроп (полный цвет) -> enhance (tools/imgproc.py, отключается --raw)
                    -> resize в --size (Lanczos + anti-ringing clamp)
                    -> энкод -> icons-<size>/<пак>/partN/icon_NNN.webp
                             + icons-<size>/manifest.json
```

Замеры (40 иконок, ошибка после приведения к 64 px, т.е. как видно в VTT):

| вариант | КБ/иконку | весь набор | ошибка 512 | ошибка при 64 px |
|---|---|---|---|---|
| палитра 255 PNG (`cut_icons/`) | 14.5 | 58 МБ | 1.43 | — (ступеньки видны) |
| **WebP q92 512 px, enhanced (по умолчанию)** | 19.9 | **79.5 МБ** | 0.86 | 0.80 |
| WebP q95 512 px, enhanced | 25.7 | 103 МБ | 0.74 | 0.76 |
| WebP q100 512 px, enhanced | 38.4 | 154 МБ | 0.61 | 0.75 |
| WebP q90 512 px без enhance (`--raw`, как было) | 21.0 | 84.2 МБ | 1.20 | 0.50 |
| AVIF q70 512 | 13.6 | 54 МБ | 1.20 | 0.61 |
| WebP lossless 512 | 112 | 450 МБ | 0 | 0 |
| палитра 256 PNG 512 | 91 | 366 МБ | — | — |

Lossless для 512 px нереален по объёму, поэтому по умолчанию lossy. q92 после
enhance занимает на 6 % меньше, чем старый q90 без него.

Про «ошибка при 64 px» стоит сказать отдельно: это средняя |разница| против
рендера исходного кропа в том же 64 px, т.е. честная потеря относительно
источника. У старого набора 0.50, у нового 0.80 — вся разница набирается
**до** энкодера (0.62) и приходится на денойз и шарп; сжатие добавляет
0.18 при q92 и 0.14 при q95. Это цена, которую платит любой денойз: пиксельно
картинка уходит от шумного оригинала на десятые доли уровня из 255 (видно в
`noise`: 0.13 → 0.03), зато в плоских местах нет ни шума, ни гало, а контуры
собраннее — на глаз это видно, а «ошибка 0.8/255» нет.

## Что именно правит enhance (`tools/imgproc.py`)

512 px — это апскейл ×3.46 кропа ~148 px, который приехал из JPEG, поэтому в
полный рост идут все четыре артефакта цепочки:

1. **шум JPEG** (москитный вокруг контуров, блочность 8×8) — уходит фильтром
   Гайдеда, направляемым яркостью, `denoise = 0.014` (радиус 1);
2. **звон ресемплера** — яркая кайма внутри силуэта и тёмная снаружи: у
   Ланцоша предел перелёта — 19 уровней из 255 на светлом объекте по чёрному
   фоне. В `resample_ar` результат клампится диапазоном пикселей, из которых
   он собран, поэтому перелёта нет вообще (для этого свой ресемплер, у Pillow
   доступа к тапу нет; проверено — при `stretch=False` он совпадает с
   `PIL.LANCZOS` до 0.18/255);
3. **пиксельная лестница** исходных 148 px — размытие *вдоль* контура
   (`steered_blur`, структура тензора + range-вес поперёк): ступеньки
   спрямляются, профиль края не трогается, плоские и шумные места гейтятся
   когерентностью;
4. **мягкие контуры** — unsharp с порогом и клампом (±13 уровней): контраст
   края растёт, шум не усиливается, гало нет. Обычный unsharp/CLAHE на этом
   арте даёт видимые гало и потому не используется.

Чёрный фон листов (после JPEG он не ровно 0) дополнительно подтягивается к 0
ниже `--black 0.010`.

### Замеры качества (`tools/measure_quality.py`)

10 листов (иконки 17/3-й четверти каждого листа; `noise`/`bleed` — уровни из
255, `width` — px, `hf` — энергия мелкой текстуры относительно честного
ресaйза, `err@64` — средняя ошибка при показе в 64 px):

| стадия | noise | bleed | bleed p99 | overshoot | width | hf | err@64 |
|---|---|---|---|---|---|---|---|
| честный resize (как было) | 0.14 | +0.01 | +0.13 | 0.484 | 1.48 | 1.00 | 0.16 |
| + anti-ringing resize | 0.14 | +0.01 | +0.07 | 0.409 | 1.41 | 0.98 | 0.23 |
| + denoise | 0.06 | +0.00 | +0.01 | 0.343 | 1.39 | 0.93 | 0.58 |
| + black floor | 0.04 | +0.00 | +0.00 | 0.347 | 1.40 | 0.94 | 0.60 |
| + steered blur | 0.04 | +0.00 | +0.00 | 0.426 | 1.46 | 0.88 | 0.67 |
| **+ masked unsharp (полный)** | **0.04** | **+0.00** | **+0.00** | 0.575 | **1.38** | 0.93 | 0.62 |
| **новый набор `icons-512` (q92)** | **0.03** | **+0.01** | **+0.26** | 0.490 | 1.39 | 0.97 | 0.80 |
| старый набор `icons-512` (q90, без enhance) | 0.13 | +0.02 | +0.45 | 0.377 | 1.41 | 1.02 | 0.50 |

Наглядно: `docs/qa-audit/enhance-before-after.png` (слева старый набор, справа
новый, кропы 1:1 ×2).

То же сравнение по всему набору (каждая третья иконка, 1366 штук — старый
набор против нового, замер по готовым файлам):

| метрика | старый набор | новый набор |
|---|---|---|
| noise (медиана по иконкам) | 0.112 | **0.037** |
| noise, p90 по иконкам | 0.285 | **0.135** |
| bleed | 0.016 | **0.008** |
| bleed p99 | 0.457 | **0.237** |
| bleed p99 по иконкам | 0.890 | 0.701 |
| иконок с bleed p99 > 1 | 4 | **0** |
| width (длина перехода края) | 1.407 | **1.340** |
| hf (мелкая текстура) | 1.036 | 0.948 |
| err@64 | 0.484 | 0.808 |

Как это читать:

* `noise` — СКО ВЧ-остатка в плоских областях (маска строится на нативном
  кропе: диапазон 3×3 < 2 %, т.е. там шум заведомо артефакт): **0.13 → 0.03**
  на готовых наборах и 0.14 → 0.04 по стадиям;
* `bleed` — насколько тёмный пиксель вылез выше самого яркого пикселя
  источника в своей нативной окрестности, т.е. свет, которого в арте не было
  (гало). У старого набора +0.02 в среднем и +0.45 в p99, у нового в среднем
  +0.01 (это уже сам WebP), а p99 упал с 0.45 до 0.26: кайма убрана,
  у остальных иконок она на уровне арта;
* `width` — эффективная длина перехода края: 1.39 px против 1.41 px у старого
  набора, т.е. контуры не размыты, а чуть собраннее;
* `hf` — 0.97 у готового набора: мелкая текстура (штриховка, блики) на месте,
  микрошум не вычищен вместе с ней;
* `err@64` — 0.80 против 0.50 у старого набора; как разложена эта разница,
  см. предыдущий раздел: это денойз и шарп (0.62 до энкодера), а не сжатие.

Осторожно с `overshoot`: метрика считает перелёт края за уровни, которые он
соединяет, по изолированным переходам — у антиалиасенного арта «перелёт» есть
и у честного ресайза (светлый купол имеет светлый рант), поэтому 0.575 полного
пайплайна — это в основном сам арт (0.484 у честного resize), а добавка
ограничена клампом шарпа (±0.05 от шага края).

```bash
.venv/bin/python tools/measure_quality.py                     # таблица выше
.venv/bin/python tools/measure_quality.py --sheets 30 --set icons-512
```

```bash
.venv/bin/python tools/repack_icons.py                        # 512 px, WebP q92, enhanced
.venv/bin/python tools/repack_icons.py --size 256 --quality 92
.venv/bin/python tools/repack_icons.py --format avif --quality 70
.venv/bin/python tools/repack_icons.py --size 0               # размер кропа как есть
.venv/bin/python tools/repack_icons.py --raw                  # как было: без enhance, Lanczos
.venv/bin/python tools/repack_icons.py --denoise 0 --steer 0 --sharpen 0   # покрутить стадии
.venv/bin/python tools/repack_icons.py --dry-run              # прикидка объёма, ничего не пишет
.venv/bin/python tools/repack_icons.py --only "Icons 39"      # один пак
```

Параметры прогона (`--denoise`, `--steer`, `--sharpen`, `--raw`) попадают в
`manifest.json` (`enhance.config`), так что набор воспроизводим из манифеста.

`manifest.json` на выходе: по каждой иконке файл, пак, часть, номер, исходный
лист, координаты ячейки, нативный размер, размер файла и md5, плюс параметры
энкодинга — база для компендиума Foundry, имён и дедупликации.
Ссылки в `manifest.json` относительны корню `icons-<size>/`.

Оба набора версионируются, чтобы клон работал без прогона тулчейна:
`cut_icons/` — 4100 палитровых PNG (58 МБ), `icons-512/` — 4100 WebP 512×512
плюс `manifest.json` (79.5 МБ). Пересобираются они из листов в корне за 1.5 и
16 минут (enhance заметно дороже простого ресайза: 0.25 с на иконку, два
процесса), так что это осознанный компромисс в пользу «git clone и всё
на месте».

## Запуск

```bash
python3 -m venv .venv
.venv/bin/pip install -r tools/requirements.txt
.venv/bin/python tools/cut_icons.py            # все листы
.venv/bin/python tools/cut_icons.py "RPG Loot Icons 39/RPG Loot Icons 39 Part 1.jpg"
.venv/bin/python tools/repack_icons.py         # 512 px WebP q92 + enhance (20 мин)
.venv/bin/python tools/qa_icons.py             # проверка палитрового набора
.venv/bin/python tools/qa_icons.py icons-512 webp   # проверка перепакованного
.venv/bin/python tools/measure_quality.py --set icons-512   # таблица стадий enhance
```

`cut_icons.py` печатает на лист: режим (`frame` / `grid`), размер найденной сетки,
размер ячейки, период и число иконок — по нему видно, что лист не «проскочил»
в неверный режим.

`tools/qa_icons.py` — быстрая проверка выхода без пересчёта детекции: число иконок,
модальный размер и выбросы, пустые/слишком мелкие кропы, дубликаты по md5.
`tools/measure_quality.py` — замеры шума/гало/деталей по стадиям enhance (таблица
выше), `tools/imgproc.py` — сами фильтры (только numpy + Pillow, без scipy/OpenCV);
`tools/scan_frames.py` — диагностика найденных рамок; `tools/analyze.py` —
низкоуровневые хелперы (серые прогоны и т.п.).
